# 09 - Cross-Questions and Rebuttals

Focus area: preventing malicious AI-generated code from escaping the sandbox or abusing CPU, memory, filesystem, or network access.

---

### Q1: "WASM is not truly secure - there have been Wasmtime CVEs. What happens if the WASM layer is bypassed?"

Acknowledged - no sandbox is impenetrable in isolation, and I engineered the system knowing that. The design assumes WASM layer bypass is a non-zero probability and layers additional controls outside the WASM runtime: the worker process runs inside a Linux network namespace with no routes configured, mounts an empty tmpfs with `noexec` and `nosuid` instead of the host filesystem, and is restricted by a seccomp-BPF profile that allowlists only the ~25 syscalls the WASM runtime actually needs. A Wasmtime CVE that gives the attacker arbitrary code execution inside the worker process still cannot reach the network (no routes), cannot persist to disk (tmpfs in-memory, cleared on process exit), and cannot spawn child processes (execve, clone with CLONE_NEWPROC are blocked by seccomp). Beyond that, workers run as non-root with a randomized UID, and Kubernetes pod security policy disallows privilege escalation. The attacker lands in a heavily constrained process with no meaningful lateral movement surface. Defense-in-depth means the WASM layer is not the last line - it is the first.

### Q2: "Fuel metering is based on instruction count, not wall clock time. Can't an attacker just use expensive native instructions to exhaust real CPU without hitting the fuel limit?"

This is a real tension and I calibrated for it. The concern is that a malicious WASM module could contain instructions that are cheap in terms of fuel count but expensive in terms of real CPU time - for example, a tight loop of SIMD shuffle operations or heavy floating-point transcendentals. The mitigation is three-layered. First, the fuel budget is calibrated empirically against the slowest realistic instruction mix using benchmarks of representative AI-generated code, not theoretical minimum instruction cost. Second, every execution is additionally bounded by a wall-clock deadline enforced by the host goroutine via context cancellation - if the fuel budget hasn't fired but the wall clock has elapsed, the goroutine calls `Close()` on the WASM instance. Third, at the OS level, the worker process lives under a cgroup `cpu.max` quota that prevents any single worker from monopolizing more than one vCPU across any scheduling period, regardless of what happens inside the WASM runtime. Fuel is the fast path; wall clock and cgroup are the backstops.

### Q3: "You block WASI sock_* imports - but what about DNS resolution that happens inside the WASM runtime's stdlib?"

Correct concern - and the answer is that DNS resolution requires a socket, and sockets require WASI socket imports, which we do not grant. The WASI linker configuration explicitly rejects any module that imports `sock_open`, `sock_connect`, `sock_send`, `sock_recv`, or any other socket-family WASI function at module load time - the module fails to instantiate before any code runs. Pyodide's Python stdlib's `socket` module uses WASM imports; those imports are refused. Even if an attacker embedded raw WASM instructions that tried to call a host function for DNS, there is no host-registered function at that import slot - the runtime raises an `unknown import` trap. Beyond that, the worker process runs in a Linux network namespace with no routes and no DNS resolver configured. Even if somehow a raw socket were opened through a runtime bug, resolution would time out with `ENETUNREACH` - there is no reachable network. Both the WASI import layer and the network namespace independently prevent DNS.

### Q4: "What prevents a tenant from using side-channel attacks to infer another tenant's data from shared CPU caches?"

This is a legitimate concern at our operating point and I want to be precise about what we can and cannot claim. CPU cache side-channels (Spectre variant 1/2, Flush+Reload, Prime+Probe) require the attacker and victim to share physical CPU resources, which is inherent to multi-tenant execution. Our primary mitigation is temporal isolation: a single worker executes one WASM instance at a time - tenants do not share a CPU core simultaneously. The pre-warm pool assigns each execution to a dedicated goroutine, and GOMAXPROCS limits concurrency to the number of vCPUs. Tenants interleave on CPU cores across scheduling quanta but not simultaneously. We also enable Spectre mitigations in the kernel (IBRS, STIBP, SSB) and validate that the worker nodes are not running on hyperthreading-exposed sibling threads for sensitive workloads. Where the design is honest about its limits: if two tenants are scheduled on the same physical core in rapid succession, Flush+Reload attacks remain theoretically possible. For customers requiring stronger guarantees, the architecture supports dedicated worker pools - a cluster of workers assigned exclusively to one tenant's executions, scheduled on a dedicated node pool. At BlackBox, the standard tier uses shared workers; dedicated-node mode is the Enterprise tier offer that maps to the SOC-2 Type II control for high-sensitivity tenants.

### Q5: "If you pre-warm a pool of WASM instances for performance, how do you guarantee no state leaks between executions?"

The key is distinguishing between the compiled module (immutable bytecode, shared safely) and the module instance (mutable linear memory, created fresh per execution). The pre-warm pool holds goroutines that are ready to call `InstantiateModule` quickly - they do not hold live instances between executions. When an execution completes, `module.Close()` is called, which frees the linear memory entirely. The goroutine then calls `InstantiateModule` again on the cached `CompiledModule` to prepare for the next execution. The new instance gets a freshly allocated linear memory initialized from the module's data segments - byte-for-byte identical to what a cold instantiation would produce. There is no reuse of the prior execution's heap. To verify this in production, I added an assertion layer during staging: after module close, we inspect the freed memory region (before it is returned to the allocator) and confirm it contained no sentinel markers we planted at the start of the previous execution. This is not the production path - it is a correctness test we ran continuously in staging to build confidence before Enterprise launch. The guarantee is: fresh linear memory per execution by construction, not by assumption.

### Q6: "Your seccomp profile allowlists mmap and mprotect. Can't a sandbox process use these to write shellcode and execute it?"

Yes, mmap with `PROT_WRITE | PROT_EXEC` would allow writing and executing shellcode. We block that specific combination. The seccomp rule uses argument filtering (seccomp `SECCOMP_RET_ERRNO` with BPF argument inspection): `mmap` is permitted only with `prot` that does not include `PROT_EXEC`; `mprotect` is permitted only when it does not set `PROT_EXEC` on a previously writable region. This is enforced via a BPF program that inspects the `prot` argument at the syscall level - the syscall returns `EPERM` if the attacker tries to mark memory executable. The WASM JIT compiler (Wasmtime's Cranelift / wazero's compiler) needs `mprotect` to mark JIT-compiled pages executable, but it does this during module compilation at startup - not during user code execution. We separate the compilation phase (which runs before user code and is permitted to use mprotect) from the execution phase (where we apply a tighter seccomp profile that forbids new executable mappings). The JIT output pages are marked read-execute before user code runs, and no new writable-then-executable transitions are permitted during execution.

### Q7: "How would you handle a WASM module that deliberately inflates its heap to exhaust the host's memory before the runtime limit kicks in?"

The WASM memory limit is enforced before OS memory is allocated. When Python inside Pyodide calls `list([0] * 10**9)`, it triggers `wasm_memory_grow` instructions inside the WASM runtime. The runtime checks the requested page count against the configured maximum (`WithMemoryLimitPages`, e.g., 2048 pages = 128MB). If the request would exceed the cap, the runtime returns `-1` from `wasm_memory_grow` - a standard WASM signal meaning "growth denied" - before calling `mmap` on the host. Python's allocator receives an out-of-memory signal, which surfaces as a Python `MemoryError` in the user's code, not a host OOM. The host process's RSS never exceeds the worker's base footprint plus the capped linear memory. Belt-and-suspenders: the Kubernetes pod has a `resources.limits.memory` set to worker_count × (base + max_linear_memory) + headroom. If something in the JIT or runtime itself leaks memory outside the WASM linear memory model, the pod is OOM-killed by kubelet, a new pod starts from the pre-built image, and the load balancer stops routing to the dying pod during its readiness probe failure window.

### Q8: "What if the AI-generated code targets a known bug in Wasmtime's JIT compiler to escape the sandbox?"

This is the highest-severity threat class and I want to be direct: a zero-day in the WASM runtime's JIT is the most dangerous vector, and the defense is depth, not prevention. The WASM layer is not the last control. At the process level: the worker runs with a minimal seccomp allowlist (no execve, no ptrace, no socket creation), inside a mount namespace with only tmpfs, inside a network namespace with no routes, as a non-root UID. A JIT escape that gives the attacker arbitrary code execution in the worker process still cannot reach the network, cannot run new binaries (execve blocked), cannot pivot to other pods (no routes), and cannot read persistent disk (tmpfs only). At the cluster level: workers run on dedicated node pools with no access to the Kubernetes API server (RBAC + NetworkPolicy blocks pod-to-API communication). At the response level: we subscribe to Wasmtime security advisories and the CVE feed; our container images are rebuilt and redeployed within 24 hours of a critical runtime advisory. Wasmtime's own security model explicitly states that sandbox escapes are severity-critical and are patched with priority. The combination of rapid patching cadence, process-level defense-in-depth, and network namespace isolation limits the blast radius of a JIT CVE to the lifetime of one worker process before it is killed and replaced.

### Q9: "SOC-2 requires proof of isolation. How do you prove mathematically or empirically that two tenants cannot affect each other?"

We approach this on two tracks: formal claims and empirical validation. On the formal side: WASM's memory model is specified in the WebAssembly specification. The linear memory of instance A is a distinct byte array from instance B's; no WASM instruction addresses memory outside its own instance's linear memory. This is a property of the WASM specification itself, independently verified by the academic community and embedded in the language semantics - not a runtime configuration we can misconfigure. On the empirical side: during our SOC-2 Type II audit, we ran a controlled isolation test suite. Two concurrent execution streams - one writing known sentinel values to every address in its linear memory, one reading every address in its linear memory and asserting they contain only its own initialized values - ran for 24 hours without a single cross-tenant read. We also ran resource exhaustion tests: one tenant exhausted its fuel budget and memory limit; we verified the other tenant continued to execute normally with no latency increase beyond expected scheduling noise. The audit artifacts included this test report, the WASM specification section on memory isolation, and our seccomp + namespace configuration. From my time standardizing threat modeling at Microsoft, I know auditors respond to evidence chains, not assertions - so we gave them a test methodology they could re-run, not just a policy document.

### Q10: "If a module runs out of fuel, it traps. But WASM traps are recoverable - couldn't the host recover and retry, letting the code run indefinitely?"

The WASM trap is recoverable at the host level - the host goroutine gets a `TrapError` and can choose what to do next. But our execution model does not retry on trap. When a fuel exhaustion trap is received, the host goroutine: (1) calls `module.Close()`, which frees the linear memory and invalidates the instance; (2) writes an `EXECUTION_TIMEOUT` event to the SSE stream; (3) returns an error to the caller. The module instance is destroyed - not suspended and not retried. There is no mechanism for the caller to resume execution from the point of trap because the module's linear memory has been freed. To verify this is operationally enforced: the scheduler tracks a `max_retries = 0` policy for fuel trap errors (distinct from transient infra errors where retry with backoff is appropriate). The retry policy is part of the scheduler configuration, not the hot execution path, so it can be audited and tested independently. I also want to note the asymmetry: a trap is a hard stop at the point of exhaustion, not a pause. Re-running the module from the beginning would not help an attacker - they'd hit the same fuel limit. The only useful attack would be if the host retried with a new fuel budget, which our policy explicitly prevents.

### Q11: "What about supply-chain attacks - what if the WASM binary itself contains a JIT-spraying payload embedded by the AI model?"

JIT spraying against a WASM JIT compiler is a real attack class: the attacker crafts a WASM module whose constant values, when JIT-compiled, leave attacker-controlled bytes at known offsets in the JIT output code pages. Combined with a memory corruption bug in the JIT, the attacker redirects execution into the sprayed payload. Our mitigations: first, we validate the WASM module binary before instantiation - we run a structural validator (wazero's built-in validator, which checks type correctness, stack balance, and instruction legality per the spec) and reject malformed modules without ever reaching the JIT. This eliminates modules crafted to trigger parser bugs before JIT runs. Second, we run the JIT on the module in an isolated compilation goroutine with a separate memory quota - JIT compilation memory overhead is bounded and monitored. Third, the JIT output is ASLR-randomized; without an info leak, spraying requires brute force across a very large address space. Fourth, and most importantly: the seccomp profile blocks `mprotect` with `PROT__WRITE | PROT_EXEC` together (W^X enforcement at the syscall level). A JIT spray that attempts to write to code pages after JIT compilation is complete is blocked by the kernel before it runs. The defense is not "prevent malicious WASM input" - it is "even if the JIT is exploited, the post-exploitation path is blocked."

### Q12: "At 1M+ executions/day, your seccomp profile is applied per-worker-process at startup. What if a worker process serves 10K executions and is eventually compromised - how do you limit blast radius?"

Worker process lifetime is bounded explicitly. Each worker process is retired after a configured execution count limit (e.g., 500 executions) and a wall-clock lifetime limit (e.g., 30 minutes), whichever comes first. After the limit, the worker completes its in-flight execution, drains, and exits cleanly - the supervisor process starts a fresh replacement. This limits the number of executions any single compromised worker could have observed to 500, not 10K. The execution count limit is set conservatively enough that even if an attacker tried to exfiltrate historical data from worker memory, the window is small. Beyond worker lifetime: each worker's process memory is isolated from other workers (separate address spaces, separate PIDs). A compromised worker cannot read another worker's memory. The blast radius of a single compromised worker is bounded to: the executions that ran in that worker's lifetime, the linear memory of the currently-in-flight execution at the moment of compromise, and the worker's own tmpfs mount (which contains nothing persistent). It cannot affect Kubernetes control plane (RBAC + NetworkPolicy), the database tier (no credentials in worker env; credentials are in a separate sidecar via Vault agent injection with short-lived leases), or other workers. From my threat modeling work at Microsoft, the principle is: define the blast radius of each component failure before the component is deployed, then validate that the blast radius is acceptable. For worker compromise, the blast radius is one worker's execution window - and that window is bounded by the retirement policy.
